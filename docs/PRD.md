# Little Library Desk PRD v2.1

Oct 19, 2026 · @채수

## 1. 문서 정보 및 변경 이력

이 문서는 Antigravity에 그대로 넘겨 바이브코딩으로 앱을 만드는 것을 전제로 쓴 구현용 PRD입니다. v1.1 기획안의 Notion + Make 구조를 독립 웹앱 구조로 바꾸고, 공공 API 장애 대비책(데모 모드)을 추가했습니다.

**프로젝트명:** Little Library Desk (작은도서관 통합 운영관리툴) · 저장소 `little-library-desk` · 기준 문서 `docs/PRD.md`

| 버전 | 날짜 | 주요 변경 |
| --- | --- | --- |
| v2.1 | 2026-10-19 | 미결 사항 확정: 회계연도 1월 시작 + 분기 보고 CSV(P0), 운영위원 6명(관리자 1명), 작은도서관 키워드, 아이디어 뱅크 전국 범위, 로그인 기능 MVP 제외 |
| v2.0 | 2026-10-19 | Make 제외, Notion DB를 자체 DB로 대체, API 한도 초과 시 데모 모드 추가, 하루 업무 사이클(As-Is/To-Be) 반영, 데이터 모델·화면·바이브코딩 단계 추가 |
| v1.1 | 2026-10-08 | 최초 기획: 칸반·예산·대시보드 + 공공데이터 2종 연동, Notion + Make 파이프라인 |

**v2.0에서 확정한 결정**

- Make 등 서드파티 자동화 툴을 쓰지 않는다. 공공 API 수집은 앱이 자체 스케줄러로 직접 처리한다.
- 공공 API 호출이 한도 초과·장애로 실패하면 서비스를 멈추지 않고 데모 모드(캐시 또는 샘플 데이터)로 전환하고, 화면에 그 사실을 알린다.
- 앱은 Antigravity로 생성하며, 이 문서의 10장이 단계별 지시 프롬프트 역할을 한다.

**v2.1에서 확정한 결정**

- 회계연도는 1월에 시작한다. 연간 예산과 함께 분기(1\~4분기) 보고 자료를 CSV로 낸다.
- 운영위원은 6명이며 그중 관리자는 1명이다.
- 로그인은 MVP에서 빼고 추후 개발한다. 그동안 데이터는 서버를 통해서만 읽고 쓴다.
- 지원사업 키워드는 작은도서관 관련어로 구성하고, 아이디어 뱅크는 전국 문화행사를 수집한다.

## 2. 제품 개요

작은도서관 운영위원이 행사·예산·지원사업 정보를 한 화면에서 관리하도록, 흩어진 엑셀·카카오톡·정부 사이트 업무를 하나의 웹앱으로 묶는다.

**문제 정의**

- 소통 파편화: 업무와 예산 정보가 카카오톡, 노션, 엑셀에 흩어져 있어 현황 파악에만 매일 시간이 든다.
- 행정 지연: 영수증을 엑셀에 수기 입력하고 잔액을 따로 계산해 공유하므로 오류와 지연이 생긴다.
- 기회 누락: 지원사업 공고를 사람이 직접 찾아야 해서 마감을 놓치는 공고가 생긴다.
- 기획 리서치 부담: 행사 아이디어를 매번 검색으로 수집한다.

**목표**

1. 운영 업무(행사, 예산)를 하나의 진실 공급원(SSOT)으로 통합한다.
2. 외부 정보(지원사업, 문화행사)를 자동으로 수집해 사람이 찾지 않아도 되게 한다.
3. 포트폴리오로서 실무 밀착형 기획력과 데이터 기반 운영 역량, 장애 대응 설계 역량을 보여준다.

**타겟 사용자**

| 페르소나 | 인원 | 역할 | 주요 니즈 | 디지털 숙련도 |
| --- | --- | --- | --- | --- |
| 운영위원(관리자) | 1명 | 예산 책임, 분기 보고, 지원사업 신청 결정 | 잔여 예산과 신규 공고를 매일 확인, 분기 보고를 빠르게 작성 | 중간 |
| 운영위원(실무자) | 5명 | 행사 담당, 지출 입력 | 내 담당 행사와 할 일, 영수증 입력의 간편함 | 낮음\~중간 |
| 초기 테스터 | 기획자 본인 및 동료 | 실제 운영 데이터로 검증 | 실사용 흐름 점검 | 높음 |

**핵심 지표**

| 지표 | As-Is | To-Be 목표 | 측정 방법 |
| --- | --- | --- | --- |
| 아침 현황 파악 시간 | 약 30분 | 5분 이내 | 테스터 자가 기록 2주 |
| 지원사업 탐색 시간 | 주 2\~3회, 회당 약 1시간 | 0시간(알림 확인만) | 테스터 자가 기록 |
| 지원사업 공고 누락률 | 측정 불가 | 0% (수집 키워드 기준) | 수집된 공고 vs 기업마당 수동 검색 대조 |
| 행사 1건당 정산 처리 시간 | 측정 필요 | 50% 단축 | 지출 입력\~공유까지 소요 시간 |
| 데이터 가용률 | 해당 없음 | 화면 빈 상태 0회 (데모 모드 포함) | 수집 로그 |

As-Is 수치는 리서치 단계 추정치이며, 테스트 시작 전 1주간 실제 측정해 기준선을 다시 잡는다.

## 3. 사용자 시나리오: 하루 업무 사이클

앱을 쓰면 운영위원의 하루는 '찾고 맞추는 일'에서 '확인하고 결정하는 일'로 바뀐다. 각 시간대가 어떤 화면에 대응하는지가 곧 기능 우선순위다.

| 시간대 | 업무 | As-Is (수동) | To-Be (앱 도입 후) | 담당 화면 |
| --- | --- | --- | --- | --- |
| 09:00 | 업무 파악 | 카카오톡·노션·엑셀을 각각 열어 할 일과 잔액 대조, 약 30분 | 대시보드 한 화면에서 이번 주 할 일, 예산 소진율, 신규 공고 수 확인, 약 3분 | 대시보드 |
| 10:00 | 지원사업 탐색 | 기업마당·구청 사이트에서 키워드 수동 검색, 주 2\~3회 약 1시간 | 새벽에 수집된 신규 공고가 알림 패널에 카드로 대기, 관심 표시만 하면 됨 | 지원사업 알림 |
| 14:00 | 행사 기획 | 타 도서관·문화센터 사이트를 검색해 아이디어 수집 | 아이디어 뱅크에서 지역·분야로 필터링, 마음에 드는 카드를 행사 초안으로 바로 생성 | 아이디어 뱅크 → 칸반 |
| 16:00 | 지출·정산 | 영수증 수합 후 엑셀 수기 입력, 함수로 잔액 계산, 카톡방 공유 | 지출 입력 즉시 잔액·차트 갱신, 공유 링크로 운영진이 같은 화면 확인 | 예산 트래커 |

**대표 유저 시나리오 (한 행사의 일생)**

1. 관리자가 알림 패널에서 '작은도서관 문화프로그램 지원' 공고를 발견하고 '관심'으로 표시한다.
2. 실무자가 아이디어 뱅크에서 인근 지역의 그림책 원화전 카드를 보고 '행사로 만들기'를 누른다. 칸반 '기획' 열에 카드가 생긴다.
3. 담당자와 일정, 예산을 지정하고 '준비'로 옮긴다.
4. 준비 중 발생한 지출을 그 행사에 연결해 입력한다. 대시보드의 소진율이 바로 바뀐다.
5. 행사가 끝나면 '완료'로 옮기고, 행사별 집행액을 정산 근거로 내보낸다(CSV).

## 4. MVP 범위

MVP는 7개 기능(모두 P0)이며, 도서 대출·반납 같은 장서 관리는 기존 시스템 영역이므로 다루지 않는다.

| ID | 기능 | 우선순위 | 비고 |
| --- | --- | --- | --- |
| F1 | 운영 현황 대시보드 | P0 | 모든 기능의 요약이 모이는 첫 화면 |
| F2 | 행사·프로그램 칸반보드 | P0 | 상태 4단계, 담당자, 일정, 연결 예산 |
| F3 | 예산·지출 트래커 | P0 | 1월 시작 회계연도, 총예산 자동 차감, 분기·카테고리·행사별 차트 |
| F4 | 지원사업 자동 알림 패널 | P0 | 기업마당 API, 작은도서관 키워드, 매일 새벽 수집 |
| F5 | 문화행사 아이디어 뱅크 | P0 | 한국문화정보원 API, 전국 범위, 매일 새벽 수집 |
| F6 | 데모 모드 / 데이터 상태 표시 | P0 | API 실패 시 캐시·샘플 데이터로 전환 |
| F7 | 분기 보고·정산 CSV 내보내기 | P0 | 기존 분기 보고 문서 양식에 맞춘 CSV |

**이번 범위에서 제외 (Out of scope)**

- 로그인·회원 인증 (추후 개발, 데이터 구조는 미리 대비)
- 도서 대출·반납, 장서(MARC) 관리
- 카카오톡 알림 발송, 이메일 발송
- 영수증 OCR, 회계 시스템 연동
- 다중 도서관(멀티 테넌트) 지원
- 모바일 네이티브 앱 (반응형 웹으로 대응)
- Make, Zapier 등 서드파티 자동화 툴

**사용 방식 (로그인 없음)**

- 운영위원 6명이 같은 배포 주소로 접속해 함께 쓴다. 주소는 운영진 내부에만 공유한다.
- 사람 구분은 로그인 대신 '운영위원 명단'에서 고른다: 행사 담당자, 지출 입력자 선택 시 사용.
- 관리자 전용이던 기능(총예산 설정, 카테고리·키워드 수정, 명단 관리)은 설정 화면에 모으고, 저장 전 확인 대화상자를 띄운다.
- 로그인 도입 시 명단의 각 운영위원에 계정을 연결하고 관리자 1명에게 권한을 주는 방식으로 확장한다.
- 포트폴리오 공개용은 DEMO\_MODE=true의 별도 배포로 운영해 실제 운영 데이터와 분리한다.

## 5. 기능 상세 명세

각 기능은 유저 스토리, 요구사항, 수용 기준(완료 판단 조건) 순으로 적는다. Antigravity 에이전트에게는 수용 기준을 테스트 체크리스트로 주면 된다.

### F1. 운영 현황 대시보드

**유저 스토리:** 운영위원으로서, 아침에 한 화면만 보고 오늘 챙길 일과 예산 상태를 알고 싶다.

- 상단 KPI 카드 4개: 총예산 / 집행액 / 잔액 / 소진율(%), 그 아래 이번 분기 집행액과 분기 보고 바로가기
- 이번 주 할 일: 이번 주(월\~일)에 시작하거나 마감인 행사 목록, 담당자 표시
- 진행 중 행사: 상태가 '준비' 또는 '진행'인 행사 카드 최대 5개
- 신규 지원사업: 최근 7일 내 수집된 공고 수와 마감 임박(D-7 이내) 공고 3개
- 오늘의 아이디어: 아이디어 뱅크 최신 카드 3개
- 데이터 상태 표시: 마지막 수집 시각과 정상/데모 모드 배지

**수용 기준**

- [ ] 지출을 추가하면 대시보드로 돌아왔을 때 잔액과 소진율이 새로고침 없이 반영된다
- [ ] 소진율 80% 이상이면 경고 색, 100% 초과면 위험 색으로 표시된다
- [ ] 각 카드를 누르면 해당 상세 화면으로 이동한다
- [ ] 데이터가 하나도 없을 때 빈 상태 안내 문구와 '첫 행사 만들기' 버튼이 보인다

### F2. 행사·프로그램 칸반보드

**유저 스토리:** 행사 담당자로서, 내 행사가 어느 단계인지 보고 끌어서 상태를 바꾸고 싶다.

- 열 4개: 기획 → 준비 → 진행 → 완료
- 카드 필드: 행사명, 담당자(멤버 중 선택), 시작일·종료일, 배정 예산, 집행액(연결된 지출 합계), 설명, 출처 아이디어 링크(선택)
- 드래그 앤 드롭으로 상태 변경, 카드 클릭 시 상세 편집 패널
- 필터: 담당자, 기간 / 보기 전환: 칸반 ↔ 목록

**수용 기준**

- [ ] 카드를 다른 열로 옮기면 새로고침 후에도 상태가 유지된다
- [ ] 카드의 집행액이 배정 예산을 넘으면 카드에 초과 표시가 뜬다
- [ ] 아이디어 뱅크에서 만든 행사는 '기획' 열에 생기고 원본 아이디어 링크를 가진다
- [ ] 모바일 폭(375px)에서는 열이 가로 스크롤 또는 탭으로 전환된다

### F3. 예산·지출 트래커

**유저 스토리:** 실무자로서, 영수증 하나를 30초 안에 입력하고 잔액이 바로 맞춰지길 원한다.

- 회계연도별 총예산 설정 (관리자만)
- 지출 입력 필드: 날짜, 금액(원), 카테고리, 연결 행사(선택), 메모, 결제수단
- 카테고리 기본값: 강사비, 재료비, 홍보비, 다과비, 도서구입비, 기타 (관리자가 수정 가능)
- 자동 계산: 잔액 = 총예산 − 지출 합계 (DB 뷰 또는 서버 계산, 클라이언트 수기 계산 금지)
- 시각화: 카테고리별 도넛 차트, 월별 집행 막대 차트, 행사별 집행 표
- 지출 목록: 최신순, 기간·카테고리·행사 필터, 수정·삭제

**수용 기준**

- [ ] 금액은 0보다 큰 정수만 허용하고 천 단위 콤마로 표시한다
- [ ] 지출 저장 후 잔액, 차트, 대시보드 KPI가 동일한 값을 보여준다
- [ ] 지출 삭제 시 확인 대화상자가 뜨고, 삭제 후 잔액이 복원된다
- [ ] 잔액이 음수가 되면 저장은 허용하되 경고 배너를 띄운다

### F4. 지원사업 자동 알림 패널

**유저 스토리:** 관리자로서, 도서관이 신청할 만한 지원사업을 직접 찾지 않고 매일 아침 받아보고 싶다.

- 수집: 매일 새벽 04:00(KST) 기업마당 지원사업 API 호출
- 필터: 공고명·사업요약·해시태그에 작은도서관 관련 키워드(기본값: '작은도서관', '도서관', '독서', '독서문화', '책', '그림책', '도서관 프로그램', '생활SOC', '마을공동체' — 설정에서 수정 가능)가 포함된 공고만 저장
- 중복 제거: 공고 ID(pblancId) 기준 upsert
- 카드 필드: 공고명, 소관기관, 신청기간, D-day, 요약, 원문 링크, 새 공고 배지
- 사용자 액션: 관심 / 보류 / 제외 표시, 관심 공고는 대시보드 상단 고정
- 정렬: 마감 임박순(기본), 최신 수집순

**수용 기준**

- [ ] 같은 공고가 두 번 수집돼도 카드는 하나만 보인다
- [ ] 마감이 지난 공고는 자동으로 '마감' 탭으로 이동한다
- [ ] 키워드 설정을 바꾸면 다음 수집부터 반영되고, 기존 데이터에도 재필터 버튼으로 적용할 수 있다
- [ ] 원문 링크는 새 탭으로 열린다

### F5. 문화행사 아이디어 뱅크

**유저 스토리:** 기획 담당자로서, 주변 지역에서 요즘 어떤 문화행사가 열리는지 보고 우리 도서관 행사의 실마리를 얻고 싶다.

- 수집: 매일 새벽 04:10(KST) 한국문화정보원 '한눈에보는문화정보' API 호출, 오늘부터 30일 이내 행사
- 수집 범위: 전국 (화면의 지역 필터는 선택 사항, 기본값 '전체')
- 카드 필드: 행사명, 분야(공연·전시·교육 등), 기간, 장소, 지역, 썸네일, 원문 링크
- 사용자 액션: 북마크, 메모, '행사로 만들기'(F2 기획 열에 카드 생성)
- 필터: 지역, 분야, 기간, 키워드 검색

**수용 기준**

- [ ] 썸네일이 없으면 분야별 기본 이미지가 보인다
- [ ] '행사로 만들기'를 누르면 행사명·설명이 미리 채워진 편집 패널이 열린다
- [ ] 종료된 행사 카드도 북마크했다면 계속 보인다

### F6. 데모 모드 / 데이터 상태 표시

**유저 스토리:** 사용자로서, 공공 API가 막혀도 빈 화면 대신 쓸 수 있는 데이터를 보고, 그 데이터가 실시간이 아니라는 사실도 알고 싶다.

- 전환 조건: API 응답이 일일 호출 한도 초과(에러코드 22), 초당 한도 초과(23, 3회 재시도 후), 타임아웃(05), 5xx, 인증키 오류일 때
- 폴백 1순위: DB에 남아 있는 마지막 정상 수집 데이터(캐시) 사용, 상태 = 'cached'
- 폴백 2순위: 캐시가 비어 있으면 저장소에 포함된 샘플 JSON(seed) 사용, 상태 = 'demo'
- 화면 표시: 상단 배너 '공공데이터 연결이 일시적으로 제한되어 \[날짜 시각\] 기준 데이터를 보여드립니다' + 해당 패널의 배지(실시간 / 캐시 / 데모)
- 복구: 다음 정상 수집이 성공하면 자동으로 실시간 상태로 돌아오고 배너가 사라진다
- 수동 전환: 환경변수 DEMO\_MODE=true면 API를 호출하지 않고 항상 샘플 데이터 사용 (포트폴리오 공개 배포용)
- 기록: 모든 수집 시도는 sync\_logs에 결과·에러코드·건수와 함께 저장

**수용 기준**

- [ ] 잘못된 API 키로 수집을 실행해도 앱은 오류 화면 없이 캐시 또는 데모 데이터를 보여준다
- [ ] 배너와 배지가 실제 데이터 출처와 항상 일치한다
- [ ] DEMO\_MODE=true 상태에서는 외부 API 호출이 0건이다 (로그로 확인)
- [ ] 설정 화면에서 최근 수집 이력 10건을 볼 수 있다

### F7. 분기 보고·정산 CSV 내보내기

**유저 스토리:** 관리자로서, 분기가 끝나면 기존에 쓰던 분기 보고 양식 그대로 CSV를 받아 바로 제출 자료로 쓰고 싶다.

- 분기 기준: 1월 시작 회계연도의 1분기(1\~3월), 2분기(4\~6월), 3분기(7\~9월), 4분기(10\~12월)
- 내보내기 종류 2가지
  - 분기 보고 CSV: 기존 분기 보고 문서의 컬럼 순서·명칭·합계 행을 그대로 따른다 (양식 확보 후 확정)
  - 지출 상세 CSV: 기간·행사 선택, 컬럼은 날짜, 행사, 카테고리, 금액, 결제수단, 메모, 입력자
- 예산 화면에 분기 탭(연간·1Q\~4Q)을 두고, 분기별 집행액·카테고리별 합계·분기 말 잔액을 보여준다
- 인코딩: 엑셀에서 한글이 깨지지 않도록 UTF-8 BOM, 금액은 숫자형(콤마 없이)
- 파일명: `{도서관명}_{연도}_{분기}Q_분기보고.csv`

**수용 기준**

- [ ] 분기 보고 CSV를 엑셀로 열면 기존 양식과 컬럼 순서·명칭이 일치한다
- [ ] 분기 합계가 예산 화면의 분기 집행액과 같다
- [ ] 분기 경계일(3/31, 4/1 등)의 지출이 올바른 분기에 들어간다
- [ ] 지출이 없는 분기도 0원으로 된 보고서가 만들어진다

## 7. 데이터 모델

테이블은 9개이며, 모든 업무 데이터는 `library_id`로 묶어 나중에 여러 도서관으로 확장할 수 있게 둔다. 금액은 원 단위 정수(`bigint`)로 저장한다.

| 테이블 | 주요 컬럼 | 설명 |
| --- | --- | --- |
| `libraries` | id, name, region, fiscal\_year\_start(=1) | 도서관 정보 (MVP는 1개, 회계연도 1월 시작) |
| `members` | id, library\_id, name, role(admin·member), is\_active, user\_id(null, 로그인 도입 시 사용) | 운영위원 명단 6명, 관리자 1명 |
| `budgets` | id, library\_id, fiscal\_year, total\_amount | 회계연도별 총예산 |
| `expense_categories` | id, library\_id, name, sort\_order | 지출 카테고리 |
| `events` | id, library\_id, title, status(planning·preparing·running·done), owner\_id(members), start\_date, end\_date, allocated\_amount, description, source\_idea\_id | 행사·프로그램 |
| `expenses` | id, library\_id, budget\_id, event\_id(null 허용), category\_id, spent\_on, amount, payment\_method, memo, created\_by(members) | 지출 내역, 입력자는 명단에서 선택 |
| `grants` | id, external\_id(pblancId, unique), title, agency, apply\_start, apply\_end, summary, url, hashtags, matched\_keywords, user\_status(new·interested·hold·excluded), source(live·seed), fetched\_at | 지원사업 공고 |
| `culture_ideas` | id, external\_id(unique), title, realm, start\_date, end\_date, place, area, thumbnail\_url, url, bookmarked, memo, source(live·seed), fetched\_at | 문화행사 아이디어 (전국) |
| `sync_logs` | id, source(bizinfo·culture), started\_at, finished\_at, status(success·fallback\_cache·fallback\_seed·failed), error\_code, fetched\_count, inserted\_count, message | 수집 이력과 데모 모드 판단 근거 |

**뷰와 계산 규칙**

- `budget_summary` 뷰: 회계연도별 total\_amount, spent(지출 합계), remaining, burn\_rate(%)
- `quarter_summary` 뷰: 연도·분기(1\~4)·카테고리별 spent, 분기 말 누적 집행액과 잔액. 분기는 `extract(quarter from spent_on)`로 계산 (1월 시작이라 달력 분기와 같음)
- `event_spend` 뷰: 행사별 allocated\_amount, spent, over\_budget(불리언)
- 데이터 상태는 소스별 최신 `sync_logs` 1건으로 결정: success → 실시간, fallback\_cache → 캐시, fallback\_seed → 데모

**관계 요약**

- libraries 1 : N members, budgets, events, expenses, expense\_categories
- events 1 : N expenses / culture\_ideas 1 : N events(source\_idea\_id)
- grants, culture\_ideas는 공공데이터이므로 도서관 공용 테이블로 두고, 관심·북마크 상태만 저장한다 (MVP는 도서관 1곳이라 같은 테이블에 둠)

**데이터 접근 규칙 (로그인 없음)**

- 브라우저는 DB에 직접 접근하지 않는다. 모든 읽기·쓰기는 Next.js 서버(Server Actions, Route Handlers)가 서비스 키로 처리한다.
- 모든 테이블에 RLS를 켜고 anon 역할에는 아무 권한도 주지 않는다. 로그인 도입 시 이 위에 사용자별 정책만 추가하면 된다.
- 서버는 모든 입력을 Zod로 검증한 뒤 저장한다 (금액 양의 정수, 날짜 형식, 상태 값 등).

## 8. 기술 아키텍처

Next.js 웹앱 하나가 화면, API, 수집 작업을 모두 맡고, Supabase가 DB를 맡는다(인증은 추후). Make가 하던 주기 호출은 Vercel Cron이 앱의 수집 경로를 하루 한 번 호출하는 방식으로 대체한다.

### 8.1 기술 스택

| 영역 | 선택 | 선택 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js (App Router) + TypeScript | 화면과 서버 API를 한 저장소에서, 바이브코딩 레퍼런스가 가장 많음 |
| UI | Tailwind CSS + shadcn/ui, 차트는 Recharts, 칸반은 dnd-kit | 컴포넌트 품질이 안정적이고 에이전트가 잘 다룸 |
| DB | Supabase (Postgres, RLS) — 서버에서만 접근 | 무료 플랜으로 MVP 운영 가능, 추후 Supabase Auth로 로그인 확장 쉬움 |
| 스케줄러 | Vercel Cron (`vercel.json`) | 별도 서비스 없이 하루 1회 수집, 서드파티 의존 제거 |
| 배포 | Vercel Hobby | 무료, GitHub 연동 자동 배포 |
| 검증 | Zod(입력·API 응답 스키마), Vitest(계산 로직), Playwright(주요 흐름) | Antigravity 에이전트의 브라우저 검증과 병행 |

**Vercel Hobby 플랜 제약 (설계 반영)**

- 크론은 [하루 1회까지만 허용되고, 지정한 시각의 1시간 안 어딘가에서 실행된다](https://vercel.com/docs/cron-jobs/usage-and-pricing). 새벽 수집에는 충분하다.
- 크론 일정은 UTC 기준이므로 KST 04시는 `0 19 * * *`로 적는다.
- [실패해도 자동 재시도하지 않고, 같은 호출이 두 번 올 수 있다](https://vercel.com/docs/cron-jobs/manage-cron-jobs). 따라서 수집은 external\_id 기준 upsert로 멱등하게 만들고, 실패 시 재시도는 코드 안에서 처리한다.
- 크론 경로는 `CRON_SECRET` Bearer 토큰을 검사해 외부 호출을 막는다.
- 설정 화면에 관리자용 '지금 수집' 버튼을 두어, 크론 실패 시 수동으로 다시 돌릴 수 있게 한다.

### 8.2 공공 API 연동 명세

| 항목 | 기업마당 지원사업정보 (F4) | 한눈에보는문화정보 (F5) |
| --- | --- | --- |
| 제공처 | 기업마당 (중소벤처기업부) | [한국문화정보원, 공공데이터포털](https://www.data.go.kr/data/15138937/openapi.do) |
| 호출 주소 | `https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do` | 공공데이터포털 활용신청 후 명세(Swagger)에서 확인 |
| 인증 | `crtfcKey` (기업마당에서 발급) | `serviceKey` (공공데이터포털에서 발급) |
| 응답 형식 | JSON (`dataType=json`), 목록은 `jsonArray` | XML → 서버에서 JSON으로 변환 |
| 주요 파라미터 | `searchCnt`, `pageIndex`, `pageUnit`, `hashtags`, `searchLclasId`(분야 코드) | 기간, 지역, 분야, 페이지 번호·건수 (명세 확인) |
| 사용 필드 | pblancId, pblancNm, jrsdInsttNm, reqstBeginEndDe, bsnsSumryCn, pblancUrl, hashtags | 행사명, 분야, 기간, 장소, 지역, 썸네일, 링크 |
| 호출 한도 | 공개 명세에서 확인 필요 | 개발계정 일 10,000건, 활용사례 등록 시 증설 가능 |
| 한도 초과 신호 | 응답의 `reqErr` 또는 HTTP 오류 | 에러코드 22(일일 한도), 23(초당 한도), 05(타임아웃) |

기업마당 분야 코드는 금융·기술·인력·수출·내수·창업·경영·기타 8종이라 '문화'나 '도서관' 분야가 따로 없다. 그래서 분야로 거르지 않고 최근 공고를 넉넉히(예: 200건) 받아 서버에서 키워드로 거른다. 하루 1회 수집이면 두 API 모두 한도의 1%도 쓰지 않으므로, 데모 모드는 주로 키 만료·장애·점검 상황을 대비하는 장치가 된다.

### 8.3 수집 파이프라인

1. Vercel Cron이 `GET /api/cron/sync-grants`, `GET /api/cron/sync-culture`를 호출한다 (KST 04시대).
2. 핸들러가 `CRON_SECRET`을 확인하고 `sync_logs`에 시작 기록을 남긴다.
3. `DEMO_MODE=true`면 호출하지 않고 seed 상태로 기록 후 종료한다.
4. 외부 API를 호출한다. 타임아웃 8초, 초당 한도·5xx는 1초·2초·4초 간격으로 최대 3회 재시도한다.
5. 성공: 응답을 Zod로 검증 → 키워드·지역 필터 → external\_id 기준 upsert → 상태 success 기록.
6. 실패: DB에 기존 데이터가 있으면 fallback\_cache, 없으면 `/data/seed/*.json`을 넣고 fallback\_seed로 기록한다.
7. 화면은 소스별 최신 sync\_logs를 읽어 배너와 배지를 그린다.
